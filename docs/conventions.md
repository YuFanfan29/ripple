# Conventions

These conventions keep the codebase consistent. If one gets in the way, change it here through a pull request instead of ignoring it.

## Language

Everything in this repository is written in English: code, identifiers, comments, commit messages, pull requests, documentation, log messages, and error messages.

The one exception is `README.zh-CN.md`, a Simplified Chinese translation of `README.md` for Chinese-speaking readers. `README.md` is the source of truth: when it changes, update the translation in the same pull request.

Prefer the standard industry term to a literal translation:

| Use | Instead of |
|---|---|
| load test, stress test | pressure test |
| ship, deploy, go live | online (as a verb) |
| API, endpoint (for HTTP) | interface (keep this word for Java and Go interfaces) |
| canary release, gradual rollout | gray release |
| cache stampede | cache breakdown |
| primary, replica | master, slave |

A phrasal verb is two words, and its noun form is one: *roll back* and *rollback*, *set up* and *setup*, *log in* and *login*, *shut down* and *shutdown*, *back up* and *backup*.

## Domain glossary

Use these terms in code, APIs, events, and documentation.

| Term | Meaning |
|---|---|
| account | A registered user. |
| post | Text with up to 4 images. |
| author | The account that created a post. |
| follower | An account that follows another account. |
| followee | An account that is followed. In APIs, an account's followees are listed under `following`. |
| home timeline | Posts from an account's followees, newest first. |
| user timeline | Posts created by one account, newest first. |
| fan-out on write | Adding a new post's ID to every follower's home timeline when the post is created. |
| fan-out on read | Fetching recent posts from followees when a home timeline is read. |
| celebrity account | An account whose follower count is above the fan-out threshold. Its posts use fan-out on read. |
| like | One account's approval of one post. |
| hot list | Popular recent posts, ranked by a score that decays over time. |
| media | An uploaded image. |
| variant | A processed copy of a media object, such as a thumbnail. |
| notification | A message that tells an account about new followers or likes. |

## Repository layout

```text
.
├── services/
│   ├── content/   Java, Spring Boot, Maven Wrapper
│   ├── feed/      Go
│   └── media/     Go
├── internal/      Go packages shared by feed and media
├── deploy/        Docker Compose files, Nginx configuration, host provisioning
├── loadtest/      k6 scripts and the dataset generator
├── docs/          charter, conventions, ADRs, runbooks, performance log
├── .github/       CI/CD workflows and the pull request template
├── go.mod         one Go module for all Go code
└── Makefile       entry point: make up, make test, make ci
```

All Go code is one module at the repository root, `github.com/YuFanfan29/ripple`, so `feed` and `media` can share the packages in `internal/`. The `content` service is a self-contained Maven project with the group ID `io.github.yufanfan29` and the base package `io.github.yufanfan29.ripple.content`.

## Code style

### Go

- Format with `gofmt` and `goimports`, and lint with `golangci-lint`. CI fails on any finding.
- Run tests with the race detector (`go test -race`).
- Functions that do I/O take a `context.Context` as their first parameter.
- Wrap errors with context: `fmt.Errorf("load home timeline %d: %w", accountID, err)`.
- Log with `log/slog`.
- Avoid package-level mutable state. Pass dependencies explicitly.
- Package names are short, lowercase, and singular: `timeline`, not `timelineUtils` or `timelines`.

### Java

- Format with Spotless and google-java-format. The build fails on unformatted code.
- Use constructor injection. Never use field injection.
- Use records for request and response types and for value objects.
- Organize packages by feature (`post`, `follow`, `like`), not by layer (`controller`, `service`).
- Write tests with JUnit 5, AssertJ, and Testcontainers.

## HTTP APIs

- REST with JSON bodies. Paths start with a version, and resources are plural nouns: `/v1/posts/{postId}/likes`.
- JSON field names use camelCase.
- Errors use RFC 9457 problem details (`application/problem+json`).
- A POST request that creates something accepts an `Idempotency-Key` header. A retry with the same key returns the original response instead of creating a duplicate.
- Lists use cursor pagination. Requests take `limit` and `cursor`, and responses return `items` and `nextCursor`, which is absent on the last page. Clients treat cursors as opaque strings.
- Each service keeps an OpenAPI document in its directory. That document is the contract for the service's API.

## IDs and time

- Entity IDs are 64-bit integers generated by the application and ordered by creation time (Snowflake-style).
- In JSON, IDs are strings, because JavaScript cannot represent every integer above 2^53 exactly.
- Times are stored and sent in UTC. JSON uses RFC 3339 with milliseconds: `2026-11-25T09:30:00.123Z`.

## Data

- Each service owns its data. A service never reads or writes another service's tables or Redis keys; it uses that service's API or events.
- MySQL tables use plural snake_case names (`posts`, `follows`). Columns use snake_case.
- Primary keys are `id BIGINT UNSIGNED`. Foreign key columns are named after the entity: `author_id`, `post_id`.
- `created_at` and `updated_at` are `DATETIME(6)` in UTC.
- Tables use the `utf8mb4` character set and the `utf8mb4_0900_ai_ci` collation, so text can contain emoji.
- Index names are `idx_<table>_<columns>`, and unique index names are `uk_<table>_<columns>`.
- Schema changes are Flyway migrations in the owning service. A migration that has been released is never edited.
- Migrations stay compatible with the version that is already running (expand first, contract later), so deploys need no downtime.
- Redis keys start with the owning service: `feed:home:{accountId}`. Every key either has a TTL or is documented with a way to rebuild it.

## Events

- Event names are past-tense PascalCase: `PostCreated`, `PostDeleted`, `PostLiked`, `MediaUploaded`, `MediaProcessed`.
- Topics are named `<owner>.<entity>.v<major>`, for example `content.posts.v1`.
- Every event uses the same JSON envelope: `eventId` (unique, used for deduplication), `eventType`, `occurredAt`, `schemaVersion`, and `payload`.
- The message key is the ID of the entity the event is about, so events for one entity stay in order.
- Producers publish through a transactional outbox. The event is written in the same database transaction as the change it describes, and a relay publishes it to Kafka.
- Delivery is at least once. Consumers deduplicate by `eventId` and must be safe to replay.
- Schema changes are backward compatible: add optional fields only. A breaking change gets a new major version and a new topic.

## Object storage

- Access object storage only through the S3 API.
- Objects are immutable. New content always gets a new key, so served images can be cached for a long time (`Cache-Control: public, max-age=31536000, immutable`).
- Originals are private, under `uploads/{mediaId}`. Served variants live under `media/{mediaId}/{variant}`.

## Configuration and secrets

- Configuration comes from environment variables, named in UPPER_SNAKE_CASE with the service as a prefix: `FEED_REDIS_ADDR`.
- Values with units include the unit in the name: `MEDIA_MAX_UPLOAD_BYTES`, `FEED_CACHE_TTL_SECONDS`.
- `.env.example` lists every variable with a safe default or a placeholder.
- Secrets never appear in the repository, in container images, or in logs. CI reads secrets from GitHub Actions secrets and uses OIDC instead of long-lived cloud keys.

## Observability

- **Logs** are JSON lines on stdout. Every line has `time`, `level`, `service`, and `message`, plus `trace_id` and `span_id` when a trace is active. Logs never contain passwords, session tokens, or other secrets.
- **Metrics** use the Prometheus format and naming rules: snake_case, base units, `_total` for counters, and `_seconds` for durations, with a `ripple_<service>_` prefix: `ripple_feed_fanout_lag_seconds`. Every endpoint has RED metrics (rate, errors, duration). Business metrics track the charter's invariants, such as fan-out lag and counter drift.
- **Traces** use OpenTelemetry. Trace context (W3C Trace Context) travels in HTTP headers and Kafka message headers.
- **Health checks.** Each service exposes `GET /livez` (liveness) and `GET /readyz` (readiness). Readiness turns false during startup and graceful shutdown, so a deploy can drain traffic before a process stops.

## Testing

- Unit tests cover logic that does no I/O.
- Integration tests run against real MySQL, Redis, Kafka, and object storage in containers, using Testcontainers. Never mock a database or a message broker.
- Every invariant in the charter has at least one automated test, including concurrent cases.
- Tests are deterministic. Inject a clock instead of sleeping, and use fixed seeds for random data.
- A flaky test is a bug. Fix it or delete it; never make CI retry it until it passes.
- Load tests live in `loadtest/`. After every run, an invariant check compares the data with the source of truth, for example that each post's like count equals its rows in `likes`.

## Documentation

- Significant decisions are ADRs in `docs/adr/`. See [the ADR index](adr/README.md).
- Operational procedures, such as rebuilding a host or restoring a backup, are runbooks in `docs/runbooks/`.
- Performance targets and results go in `docs/performance.md`.
